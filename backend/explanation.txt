each file answers exactly one question, so any teammate can read one file in a sitting and change it without understanding the rest. It mirrors the split your existing backend already uses (client, harmonizer, db, harvest script, app). It could be squashed into two files; it would be shorter and harder to test.

The flow is a straight line. The ingest script asks the client for Phase 3 studies with posted results, a thousand per request, about fifteen requests in total, and keeps every page as JSON on disk. It then hands each study to the parser, which returns a small record: the six fields plus three child lists (race rows, drug rows, condition rows). The database layer writes those in transactions of a thousand, upserting by NCT number so re-running never duplicates. Flask then reads the file and serves JSON: a filtered list, one study, a pooled aggregate, and stats.

Why the schema has four tables instead of one. Race composition is a list per study, so it must be its own table. Drug and condition are stored twice on purpose: as the "; "-joined strings your spec asked for on the study row, and split one per row in link tables so WHERE drug = 'zolpidem' is exact and indexed. The race table keeps the label verbatim for auditing and adds a harmonized bucket so counts can be added across studies.

The hard part is the parser

Baseline tables on ClinicalTrials.gov are free-form, and the rules in parse_study.py are where the judgment lives:

- Counts are strings, sometimes "NA" or "1,203". The parser takes the "Total" column when the sponsor posted one and sums the arms when they didn't. Percentage tables are skipped.
- Race labels are whatever the sponsor typed. About 45% of race tables are the free-text "Customized" kind. An ordered regex table maps labels to ten buckets; order matters, which is why "White - Arabic/North African Heritage" lands in white, not black. Anything unrecognized goes to "other" rather than disappearing. Zero counts are kept because "reported 0" and "not reported" are different findings.
- Age range is the protocol's eligibility, not the ages of who enrolled. Missing lower bound is 0, missing upper bound is 100, and "130 Years" becomes 100.
- Sex reflects enrollment from the baseline sex table, with eligibility as fallback.
- Drug is what the experimental arms received. Placebo-like names are dropped, comparators are kept with a role so the lemborexant trial doesn't count as a zolpidem trial.

Where it's good, and where it isn't

Good:

- The rules are testable and tested. Because the parser does no I/O, every rule has a test against a real response shape. When a teammate finds a mislabeled study, they add a case and fix the regex.
- It hits the API fifteen times, ever. Raw pages stay on disk, so parsing can be re-run offline all weekend and the demo doesn't depend on venue Wi-Fi.
- Provenance everywhere. Raw labels, the table each count came from, raw age strings, source URL, fetch time. The frontend contract asks for auditable evidence and this gives it.
- Tiny footprint. Standard-library SQLite, requests, Flask. Nothing to install or run besides Python.

Not good, or not yet:

- It overlaps your existing backend. harmonize.py in Drug_Me_Finder already does a similar job and stores JSON blobs; this stores normalized columns. Two pipelines for one dataset is a maintenance tax. You should pick one, and the honest recommendation is to keep this schema and port the pieces of the old harmonizer this one lacks.
- It drops the observed ages. The old harmonizer keeps mean age and age bands from the baseline table; this only keeps eligibility bounds. If the app wants "people my age", that has to come back.
- Race bucketing is a heuristic. Mixed labels like "Black Hispanic" get forced into one bucket, and only the first race table per study is used. Expect a small error rate, and expect to tune the regexes after the first real run.
- It has never seen real data. Only fixtures. The first full ingest will surface edge cases the tests don't cover.
- It isn't the API the frontend expects. The React app wants camelCase /api/v1 shapes with scores and tiers. This is the data layer underneath; an adapter or the existing v1 blueprint still has to sit on top.
- Pooling has the usual registry caveat. Summing across trials counts people twice when extension studies re-enroll them. That's inherent to the source, but the UI should say so.
